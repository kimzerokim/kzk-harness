1. G1-G4 프레이밍은 방향은 맞지만, 현재 증거는 분리도가 낮다.  
G1(wrong-layer)와 G3(knowledge trap)는 Tailscale 단일 케이스에서 사실상 같은 현상을 다른 이름으로 분해한 수준이다.  
False positive 가능성: 권한/안전 제약 때문에 L0 제안을 보수적으로 회피했을 수 있고, 사용자 프롬프트가 내부 설정 탐색을 유도했을 수 있다.  
가장 약한 건 G3다. “Occam 위반”은 해석 레이어가 커서 N=1에서 인과로 단정하기 어렵다.  

2. 50:50는 정밀 추정이 아니라 가정치라서 현재는 과신이다.  
G2는 룰로 보완 가능하지만, 현재 설계(in-memory label count) 기준에선 오히려 50%보다 낮게 구현될 위험이 있다.  
반대로 G4는 출력 계약(`fix first, explain later`)만 강제해도 개선폭이 커서 “구조적으로 불가” 판정은 과비관이다.  
결론: 갭별로 다르다. G2/G4는 스킬 보완 여지 큼, G1/G3는 일부만 보완 가능.  

3. S1은 과설계다. 제어면(FIX-LABEL, trigger, halt-resume) 신뢰성 결함이 남아 있는데 문서·스킬 수만 늘린다.  
S3는 반대로 너무 얇다. codex 호출 안정화는 하되 G2 루프 차단의 실행 장치가 약해진다.  
S4는 사용자 명시 트리거 의존이라 자동 교정(핵심 목표)을 포기하는 설계다.  
4개 중 균형은 S2가 가장 낫다: SoT 1개 + 최소 자동가드 + Cat3 drift 차단까지 포함.  

4. S5+ 가능하고, 지금 상황엔 그게 더 합리적이다.  
S5 정의: (A) codex 호출 안정화 전용(SoT+fallback+preflight+self-check) 먼저 출시, (B) 메타갭 차단은 계측 후 2차.  
또는 새 스킬 0장으로 가려면 existing 스킬에 “2-fail pivot + 라벨 고정 검증”만 inline 추가하는 초소형 패치도 가능하다.  
핵심은 두 문제를 분리 배포해 실패 원인을 분해 가능하게 만드는 것이다.  

5. 반증 기준은 “개선 안 되면 폐기”가 가능한 수치로 잡아야 한다.  
최소 지표: codex 성공률(1회 호출 성공), 60s no-token율, 5min stuck율, empty-stdout율, non-zero+stderr 분기 포착률.  
G2 지표: 동일 라벨 2연속 실패 후 pivot 실행률, pivot 후 또 same-direction 재진입률, Q-FIX-PIVOT-FAIL 발생률.  
검증 규칙: 20~30건 pre/post 비교에서 개선이 없거나 악화면 해당 메커니즘 롤백.  

6. (a) codex 호출 에러는 재현 가능한 단기 운영 이슈고, (b) G1-G4 차단은 아직 가설 비중이 크다.  
둘을 한 설계에 묶으면 성공/실패 판정이 섞여서 학습이 안 된다.  
정합성 측면에서 분리가 맞다: 먼저 (a)만 shipping해서 안정화하고, (b)는 사례 누적 후 설계 재개.  
묶어야 한다면 최소한 acceptance criteria와 롤백을 A/B로 독립시켜야 한다.  

S1 / S2 / S3 / S4 / S5 (정의: “2단계 분리 배포 — 1차 codex 호출 안정화 전용, 2차 메타갭 차단”) 중 **S5 추천. 이유: 확실한 단기 페인포인트를 먼저 닫고, 가설성 제어 로직은 계측 근거로 축소/강화 결정 가능해서 리스크가 가장 낮다.**
